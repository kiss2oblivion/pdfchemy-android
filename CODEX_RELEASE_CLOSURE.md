## SAF publication — implementation and focused verification complete

Root cause: private worker snapshots and acceptance validated the generated bytes, but `HostOutputTransaction.commit()` subsequently opened arbitrary real destinations with `wt`. SAF providers can truncate during open and can partially replace content before returning an error. Stream closure, cancellation and PublicationCoordinator do not restore those bytes. Source-alias prevention alone does not protect an unrelated old destination.

The shared save helper made this reachable: its no-saved-folder/fallback path returned a CreateDocument URI with existing/unknown provenance. Four batch split/image-export paths also bypassed OutputPolicy's fresh-copy creation. The [complete inventory](reports/SAF_PUBLICATION_INVENTORY.md) records 88 production execution/delegation/read-only call sites and their destination classes.

Correction: the shared helper selects a folder and creates a separate uniquely named copy. Batch split/image exports use the same creation policy. A host-only registry claims fresh capabilities for one operation, checks every SAF target before opening the first batch destination, retires freshness after publication, and cleans only owned incomplete copies after writers stop. Existing/unknown SAF targets fail explicitly before opening. The worker pipe/collector model, snapshots, quotas, typed acceptance and source-alias checks remain intact.
